# Rules

## Overview

These rules are the source of truth for activity behaviour. UI restrictions
must also be enforced by controllers or policies; hiding a button is not an
authorization control.

## Activity scheduling

- `date_time` stores the activity start date and time.
- `end_time` stores the activity end date and time.
- `end_time` must be later than `date_time`.
- Attendance windows are derived from these two values. Separate
  `attendance_opens_at` and `attendance_closes_at` fields are not used.
- Activity descriptions are not collected or displayed in the current flow.

## Approval

- New submissions use `pending_approval`.
- Treasurer verification is required before final admin approval.
- Only `approved` activities can accept registrations, attendance, or evidence.
- Cancelled activities cannot generate an attendance QR.

## Registration

- Registration follows `registration_opens_at` and
  `registration_closes_at` when those values exist.
- Capacity overflow places authenticated members and guests on a waiting list.
- Only an authenticated registration with status `registered` qualifies a
  member to scan attendance or upload evidence.
- `waitlisted` and `cancelled` registrations do not qualify.

## Activity status lists

- The activity calendar page is not a status-list page. Selecting a status card
  must navigate to that status's dedicated list.
- Members see only activities they created in status-card counts and lists;
  treasurer and admin roles see the full activity scope.
- Only the approved-status list may expose actions: activity details for every
  row, plus the kertas kerja/report preview for an activity that has finished.
- Rejected, pending-approval, and treasurer-verified lists are informational
  and must not render row action controls.

## QR attendance

- `qr_code_token` is nullable and starts as `NULL`.
- The token is generated on demand by the treasurer at activity start. No other
  role, including admin, may generate or regenerate it.
- QR generation is allowed only when the activity is approved and the current
  time is between its start and end times, inclusive.
- Regeneration replaces the token, immediately invalidating older QR links.
- The standalone attendance-scanner shortcut is not shown in navigation. The
  scan route remains available only as the destination encoded in a generated
  activity QR.
- Scanning is subject to the same approved status and time range.
- Attendance is unique per `user_id` and `activity_id`.
- Manual attendance is limited to registered participants and the active
  activity period.

## Evidence photos

- Evidence is a post-activity record, not an activity-submission attachment.
- Upload is allowed only when the activity is approved and `now > end_time`.
- A registered member may upload 1–10 images per request.
- Each image must pass Laravel's image validation and be at most 8 MB.
- Files are stored on the `public` disk under `activity-evidence`.
- Each photo record belongs to one activity and one uploader.
- Deleting an activity or user cascades to its evidence-photo database records.
  File cleanup should be handled whenever photo deletion is introduced.

## Security and audit

- Server-side checks are mandatory for role, registration status, activity
  status, and schedule boundaries.
- QR regeneration records the old and new token in the audit log.
- Attendance creation records the acting user and timestamp.
- Uploaded filenames are generated by Laravel storage; original client paths
  must never be trusted.

## Report downloads

- Report buttons link to a preview state by default; they must not immediately
  return an attachment.
- `download=1` is the explicit attachment state after review.
- PDF endpoints use `render=1` only for the inline document embedded in the
  preview page.
- CSV content is represented as an HTML table during preview and generated as
  CSV only for the download response.
- Query parameters controlling report periods and filters must be retained in
  preview, render, and download URLs.
- Direct preview and download requests must repeat the same gate, role, and
  record-level authorization checks.
- A report toolbar contains only one export dropdown. PDF, CSV, and print
  choices belong inside the dropdown and must not be separate toolbar buttons.
- Do not create or link to a separate financial summary report. Financial
  totals, trends, categories, filters, transactions, and exports belong in the
  main financial report.

## Fee payment selection

- The payment form lists unpaid, partial, and overdue bills as selectable
  payment items, ordered from the oldest month.
- Paid bills from the current calendar year must remain visible as a separate,
  read-only completion record.
- A bill with `status = paid` cannot be selected or included in a new payment
  submission.
